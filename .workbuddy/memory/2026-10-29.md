# 2026-10-29

## 修复 `scripts/run-local.sh` 启动卡死 + 主密钥丢失导致的启动崩溃

### 现象一：启动卡死（脚本无任何输出，2 分钟不动）

用户跑 `./scripts/run-local.sh` 卡住，既没有横幅也没有报错。

**根因**：`gen_secret()` 里这行——

```bash
LC_ALL=C tr -dc 'a-zA-Z0-9' < /dev/urandom | head -c 32
```

两个独立的坑，都在 macOS 上实测复现：

1. **挂死**：`head -c 32` 取够 32 字节就退出，但 `tr` 仍在无限读取
   `/dev/urandom`，写端关闭后**未必**立刻收到 SIGPIPE —— 取决于 tr 当时
   卡在 read() 还是 write()。概率性地永久阻塞，表现为「启动卡住」。
   同一个命令连跑两次，一次 3 秒内返回、一次挂 2 分钟，就是这个原因。
2. **静默退出（退出码 141）**：`set -o pipefail` 下 `tr` 的 SIGPIPE 死亡会
   沿管道传出命令替换；若该替换用于**普通赋值**（`V="$(...)"`），
   `set -e` 会直接杀掉脚本，不打印任何东西。
   注意：原脚本写作 `export VAR="$(...)"` —— `export` 是特殊内建，其参数里
   的命令替换失败**不**触发 `set -e`，所以历史上没暴露；一旦改成普通赋值
   就会踩雷。这个差异很隐蔽。

**修复**：改用有界、无管道的生成方式。

```bash
gen_secret() {
  if command -v openssl >/dev/null 2>&1; then
    openssl rand -hex 16   # 32 hex chars == 32 bytes
  else
    head -c 32 /dev/urandom | od -An -tx1 | tr -d ' \n' | cut -c1-32
  fi
}
```

fallback 里 `head` 在**管道头部**（自行读完 32 字节就关闭源），下游全是有限流，
不会出现 SIGPIPE 竞态。

### 现象二：`config: decrypt api_key: cipher: message authentication failed`

启动时 `list tasks` 失败，进程直接退出。

**根因**：脚本在未显式设置 `AI_MONITOR_MASTER_KEY` 时**每次启动都随机生成新密钥**。
DB 里 api_key 是上一次密钥加密的，换密钥后 AES-GCM 认证失败 → `ListTasks` 报错
→ main.go fatal → 服务完全起不来，连管理端都进不去，无法修任务。

**三层修复**：

1. **密钥持久化**：随机生成的密钥写入仓库根 `.local-secrets`（gitignore，
   chmod 600，格式 `KEY=value`），后续启动复用。这是根治。
2. **启动不再被单个坏任务拖垮**：新增 `SqliteStore.ListTasksLenient` /
   `GetTaskLenient`，解密失败的行**保留返回**，置 `TaskConfig.SecretError`
   （`gorm:"-"`，不持久化），secrets 留空。main.go 启动路径改用 Lenient 并打 WARN。
3. **管理端可修复**：`taskResponse` 增加 `secret_error` 字段；AdminTaskHandlers.list /
   get 在遇到 `ErrMasterKeyMismatch` 时自动降级到 Lenient。UI 在任务列表顶部
   显示红色告警横幅，抽屉里 api_key 行显示「密钥无法解密，请重新填写」。
   用户在编辑页重新填 api_key → `preWrite` 用当前 cipher 重新加密 → 任务恢复。

**调度隔离**：`config.TaskConfig.Runnable()` / `config.RunnableTasks()` 过滤掉
`SecretError != ""` 的任务，避免它们进入 cron 后每个 tick 都失败 + 发通知。
所有 `sched.Reload` 调用点（main 启动、热重载回调、`POST /admin/reload`）都过这个过滤器。

### 设计取舍

用**可选接口 + 类型断言**（`config.LenientTaskLister` / `LenientTaskGetter`）
而不是往 `ConfigStore` 里加方法 —— 后者会迫使 server 包所有测试替身
（memStore / fakeStore / fakeLister）同步实现新方法，改动面大且与需求无关。

AES-GCM 的「wrong key」与「tampered data」不可区分，所以新增哨兵错误
`config.ErrMasterKeyMismatch`（文案 `config: decrypt: master key does not match
the encrypted data`），调用方用 `errors.Is` 判断。注意文案里保留了 `decrypt`
字样 —— 既有测试 `TestAESCipher_WrongKeyFail` 断言错误信息含该词。

### 脚本其他改进

- **自动重建二进制**：原逻辑只在 `./ai-monitor` **不存在**时才 `go build`，
  导致源码改了却一直跑旧二进制（本次就发现用户跑的是 4 小时前的产物，
  TLS 改动完全没生效）。改为比较 `cmd/` + `internal/` 下源文件与二进制的 mtime
  （含 `internal/webui/dist/*.js`，所以前端产物更新也会触发重建）。
  新增 `--rebuild` 强制重建。
- **长度校验对齐 Go 侧**：master key 必须**正好 32** 字节（`NewAESCipher` 要求），
  JWT secret **≥32**（`auth.MinSecretBytes`）。原来是 `<16` 就放过，会在 Go 里才失败。

## 修复「前端查询不到已经创建的任务」

### 现象

`ai-monitor.db` 里明明有两条任务（`ai-test`、`minimax`），`GET /admin/tasks`
也正常返回 200 + 两条任务，但前端任务列表页**一条都不显示**。

### 根因一（主因，前端）：v-if 链被告警横幅打断

昨天为「主密钥不匹配」加的红色告警横幅写成了 `v-else-if`，插进了
渲染表格的 `v-if / v-else-if` 链里：

```
loading → [banner v-else-if] → EmptyState v-else-if → DataTable v-else
```

`ai-test` 带着 `secret_error`，`brokenTasks.length > 0` 恒成立，链条在横幅
处短路，**EmptyState 和 DataTable 都不会渲染** —— 于是页面上只剩一条横幅，
一个任务都没有。横幅本身是无辜的，位置是致命的。

修法：把横幅从链里拿出来，用 `<template v-else>` 包住「横幅 + 空态 + 表格」
三兄弟，横幅自己用独立 `v-if`。

### 根因二（后端，同类隐患）：列表错误被吞成空列表

`ListTasksLenient` 原本返回 `(tasks, errs)`，但**列表本身失败**（DB 不可达、
某行 JSON 解不开）时也复用同一个 errs 切片返回。调用方无法区分
「这一行的密钥解不开」和「查询失败了」，于是：

- `AdminTaskHandlers.listTasks` 把错误吞掉 → 返回 200 + `{"tasks":[]}`，
  前端渲染成「你还没有任务」，一个任务都查不到，且**任何地方都不报错**；
- `relCoordinator.listTasks` 同样吞掉 → 用空列表去 `sched.Reload`，
  等于**把实例里所有任务的调度都撤掉**；
- `main.go` 启动路径同样吞掉 → 数据库挂了也照样起服务，只是监控不到东西。

改法：`LenientTaskLister.ListTasksLenient` 改成三返回值
`([]TaskConfig, []error, error)` —— 第二个是「行级问题」（密钥解不开），
第三个是「列表级失败」。三个调用点（admin_task_handlers / http / reload）
分别改成：行级问题打日志继续，列表级失败往上抛
（接口返 500、reload 直接放弃本次调度、启动直接 fatal）。

> 通用教训：**「空列表」在 UI 上和「没有任务」是同一个渲染结果**，
> 所以任何「查询失败」都必须以错误的形式冒出来，绝不能退化成空列表。
> 这次的 bug 就是这个模式的教科书案例。

### 验证

用 `@vue/compiler-sfc` + `@vue/server-renderer` 做了 SSR A/B 对照（脚手架在
`web/.verify/`，用完已删）：同一份 fixture 数据（`ai-test` 带 secret_error、
`minimax` 不带），改前渲染结果只有告警横幅，改后横幅 + 完整表格 + 两个任务名。

Go 侧新增回归测试：
- `internal/server/list_failure_test.go`：列表失败必须返 500 而不是空列表；
  reload 遇到列表失败不得用空列表覆盖调度。
- `internal/config/masterkey_test.go`：`ListTasksLenient` 的第三返回值在
  DB 关闭时必须非 nil。

### 环境注意事项（续）

- `internal/scheduler` 的 3 个用例和 `internal/probe/TestRunner_TTFT_It_Duration`
  在 HEAD（干净 worktree）上同样失败 —— **既有失败/flaky，与本次改动无关**，
  别误判成自己改坏的。
- macOS 的 BSD grep **不支持 `\|` 交替**（`grep "a\|b"` 会静默返回空），
  要用 `-E` 或改用 Grep 工具。
- `sed -i ''` 在这里会把脚本当文件名（报 `No such file or directory`），
  改文件用 Edit 工具或 Python 更稳。
