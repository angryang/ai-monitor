### 关键代码模式

**`internal/protocol/respcap.go:RespCapture`**（HAR 风格）：
```go
type RespCapture struct {
    headCap, tailCap int
    head  []byte    // first N verbatim
    tail  []byte    // last M via sliding window slice
    total int
}
func (r *RespCapture) Write(p []byte) (int, error) // io.Writer 实现
func (r *RespCapture) Snapshot() (head, tail []byte, truncated bool)
func TruncateRequest(body []byte, max int) (out []byte, truncated bool)
```

**3 个 adapter 统一 pattern**：
```go
body, _ := buildRequest(cfg)
savedBody, _ := protocol.TruncateRequest(body, protocol.DefaultRequestCapture)
req, _ := http.NewRequestWithContext(ctx, "POST", streamPath, bytes.NewReader(body))
rid := protocol.GenerateRequestID(req, a.rid)  // 接住返回值
// ... ApplyExtraHeaders ...
resp, _ := a.http.Do(req)
// ...
cap := protocol.NewRespCapture(protocol.DefaultRespHeadCapture, protocol.DefaultRespTailCapture)
tap := io.TeeReader(resp.Body, cap)
s := &stream{
    ...
    requestID: rid,
    requestBody: savedBody,
    respCapture: cap,
}
go a.consume(s, tap, httpCtx)
```

**`runner.go` Run() 在 chunk loop 退出后**：
```go
res.RequestID = stream.RequestID()
res.RequestBody = stream.RequestBody()
res.ResponseHead, res.ResponseTail, res.ResponseTruncated = stream.ResponseSnapshot()
res.RequestTruncated = len(res.RequestBody) >= protocol.DefaultRequestCapture
```

### 经验沉淀

1. **adapter 默认值改 false 后，新 PID 仍跑老 binary**：sandbox 在 `go clean -cache` + `go build -a` 后二进制 md5 都还是一样。要让新 PID 用新代码，必须 Pkill 老 PID → 完全替换文件 → 启全新 PID（同 §18.12 教训）

## ai-monitor · 主题切换 bug：亮→暗成功，暗→亮失败

### 状态：✅ 修复完成，`vue-tsc --noEmit` 干净

### 现象
用户报告："主题从亮色切换到暗色，自从暗色切换到亮色失败。"

### 根因
`web/src/components/ui/ThemeSwitcher.vue` 用 `document.documentElement.dataset.theme` 作为 `computed` 的依赖源：

```ts
const current = computed(() => {
  return document.documentElement.dataset.theme === 'light' ? 'light' : 'dark'
})
```

**Vue 3 的 reactivity 不会追踪 `DOMStringMap`（即 `dataset`）的变更**——它只追踪 reactive proxy。所以这个 computed 在 setup/mount 后永远不重算，`next` 永远是首次计算时算出的反向。

具体表现：
1. 初始 `themeRef.value === 'light'`（mount 时）→ `current = 'light'` → `next = 'dark'`
2. 用户点切换 → `setTheme('dark')` → DOM 真切到 dark ✅
3. 用户再点（想切回 light）→ `current` 仍 stale 为 'light' → `next` 仍算成 'dark' → 一直停在 dark ❌

`onClick` 里那行 `void locale.value` 是当年为了"force the i18n t to re-evaluate"的 hack，但因为根因（dataset 非响应式）没解决，根本没用。

### 修复
把主题状态提升为模块级 `ref` 作为单一数据源：

- `web/src/theme.ts`
  - 新增 `export const themeRef: Ref<AppTheme> = ref<AppTheme>(readStoredTheme())`
  - `setTheme(next)` 现在三处同步：`themeRef.value = next` + `applyDocumentTheme(next)` + `persistTheme(next)`
  - 加 `storage` 事件监听做跨标签页同步（顺手）
  - 头部注释更新：dataset 是 ref 的"投影"，ref 才是 SSoT
- `web/src/components/ui/ThemeSwitcher.vue`
  - `current` 改为 `computed(() => themeRef.value)`
  - 删除 `void locale.value` 这个无效 hack
  - 头部注释写明「不要直接读 dataset.theme」的根因

### 验证
- `vue-tsc --noEmit -p web` exit 0，无输出（无类型错误）
- 逻辑正确性：ThemeSwitcher 是 reactive scope 内访问 `themeRef.value`，依赖追踪正确；`setTheme` 改 ref → computed 重算 → `next/glyph/tip` 全部联动

### 经验沉淀
1. **Vue reactivity 不追踪 DOM attribute / dataset**：任何把 `document.documentElement.dataset.xxx` 或 `el.getAttribute()` 写进 `computed` / `watchEffect` 的代码都会"看起来对、跑起来不动"。Vue 3 的 reactive 边界是 JS 对象层，不是 DOM 层
2. **DOM 作为 reactive 状态的"投影"，而非"源"**：theme 切换这种场景，正确模式是 `ref` → DOM（单向），UI 从 `ref` 读。任何反向读（DOM → ref）都会破坏响应式
3. **i18n 的 `t` / `locale` 不算响应式触发器**：`void locale.value` 这种 hack 在 reactive 系统里没意义，除非 ref 值真的被改了。注释里写"force to re-evaluate"是误导性描述
4. **storage 事件可顺手补**：跨标签页同步几乎零成本（5 行），避免用户多开标签时主题不一致

## 给所有 Go 文件顶部加 SPDX 版权 header

### 操作

### 调研结果
- 全部 **62 个 .go 文件**（内部 + cmd + deploy）都缺 header
- 24 个文件已有顶层 `// package doc` 注释
- 38 个文件直接 `package xxx` 开头
- 1 个 build tag 文件（`internal/integration/integration_test.go`，含 `//go:build integration`）
- 没有 `// Code generated` 文件（不用担心生成器覆盖）

### 方案选型
- **格式选择**：SPDX 标识符 `// SPDX-License-Identifier: MIT` 而非完整 MIT 文本
  - 2 行 header，机器可读，工具链友好
  - Kubernetes / Helm / Terraform / Cilium 等主流 Go 项目都用 SPDX
- **放置策略**：版权**永远**在文件最顶部，build tag 在版权之后紧贴 package
  - 原因：Go 1.17+ 工具链严格要求 `//go:build` 紧贴 package，中间不能夹其他标识行
  - 把 build tag 放在版权后面，比放在版权前面更安全（即使工具链未来加严也不破）

### 实施
1. 写 Python 脚本 `/tmp/add-copyright.py`，避免 sed 在多模式起始（package doc / 直接 package / build tag）下的陷阱
2. 脚本逻辑：检测 `MARKERS`（`SPDX-License-Identifier: MIT` / `Copyright (c) 2026 yangchun`）做幂等
3. 干跑预览：抽样 4 类文件（build tag / 有 package doc / 直接 package / 测试文件）确认结果
4. 实际跑：62/62 全部 updated，0 skipped
5. 验证：`go build ./...` exit 0 + `go vet ./...` exit 0 + `-tags=integration ./internal/integration/...` exit 0

### Header 文本

```go
// SPDX-License-Identifier: MIT
```

### 最终状态
- 65 个 M（62 .go + 之前 3 个：README/design.md/package.json）
- 1 个 ?? LICENSE
- 全部未 commit，按用户工作流留给他下次指令

### 经验沉淀
1. **Python 比 sed 更适合批量改源码**：多模式起始（package doc / 直接 package / build tag / 生成文件）下 sed 难以正确处理，Python 用 Path + text 切分清晰可读
2. **SPDX 是现代 Go 项目的事实标准**：比 `// Licensed under the MIT License. See LICENSE ...` 多行 header 简洁，工具链（reuse / scancode / github license detection）都识别
3. **build tag 紧贴 package 是 Go 工具链硬性要求**：注释和空行不破坏 build tag 识别，但其他标识行（package 关键字、import 关键字等）会破坏。脚本里把版权放在 build tag 之前而非之间，是最稳妥的布局

5. **幂等性检查用 markers 而非文件比对**：标记 `SPDX-License-Identifier: MIT` 比 hash 文件内容更鲁棒——再次运行不会因为 git 自动换行等小变化而漏改

- **目标读者**：后端工程师 / SRE / AI 应用开发者
- **长度控制**：~200 行 / 10K 字节。读者会跳读，骨架比细节重要

### 文章骨架（11 段）
1. **标题 + 一句话定位**（hook）
2. **写这个工具的起因**（痛点：传统工具不识别 LLM 流式特性）
3. **它能做什么**（9 维度能力表）

6. **指标一览**（8 个指标 + 表）
7. **四条内置告警规则**（动机 + 设计）
8. **工程上的小细节**（X-Req-Id / AES-GCM / scratch Docker）
9. **Roadmap**（已完成 / 接下来想做）
10. **它适合谁 / 不适合谁**（显式排除场景避免误用）
11. **参与 / 反馈 + 一句话总结**

### 输出位置
- `/Users/yangchun/code/gitlab/aibench/outputs/promote-article.md`
- 项目里没有 `outputs/` 目录，新建（不在 .gitignore，需要时再 ignore）
- 用户未要求 commit

### 经验沉淀
1. **推广文要有"显式不适合谁"**：很多 tech blog 只吹优点，结果引来一堆错配场景的用户。**明确写"不太适合 X"反而能筛掉 80% 无效流量**
2. **架构图用 ASCII 不用图片**：项目 README 里就用了 ASCII 图——保持风格一致；ASCII 图在 GitHub / 公众号 / 个人博客都能直接渲染；不用 PNG 不用 SVG
3. **"动机 > 功能"是技术文的 hook**：用户读推广文不是要 spec，是想知道"为什么需要这个"。起因写清楚，读者自己会判断要不要继续读
4. **指标 + 告警放一起讲**：指标和告警是耦合的——告警规则引用指标阈值，单独写一段读者要在两节间跳。**先讲指标再讲告警，能自然过渡**
5. **结尾的"一句话总结"是定海神针**：长文读到最后容易忘核心价值，加一个 box 让读者能扫一眼就带走 30 秒讲清楚这个项目的版本
