## ai-monitor · SPA 启动报"访问报错"修复

### 症状
- 后端服务正常：9090 端口在听、PID 进程在跑、`/healthz` 返回 `{"status":"ok"}`
- 但浏览器访问 `http://localhost:9090/` 报错（截图所示）
- 后端日志没有任何相关错误，curl `/healthz` 也 200

### 根因（半小时卡点）
- `internal/server/static.go` 的 `spaHandler` 用 `http.FileServer(http.FS(fsys))` serve 前端
- 每次 SPA fallback 都把 `r2.URL.Path = "/index.html"`，再交给 fileServer
- 但 Go 标准库 `net/http.serveFile` 有硬编码：
  ```go
  if strings.HasSuffix(r.URL.Path, "index.html") {
      localRedirect(w, r, "./", true)   // 把 /foo/index.html → /foo/
      return
  }
  ```
- 后果：浏览器 GET `/` → 301 Location: `./` → 相对解析还是 `/` → 再 301 → 无限循环 → ERR_TOO_MANY_REDIRECTS / 白屏

### curl 验证步骤（先怀疑后端，缩到静态资源）
```
$ curl -i http://127.0.0.1:9090/healthz       # 200 OK  ← 进程活着
$ curl -i http://127.0.0.1:9090/              # 301 Location: ./ ← 命中根因
$ curl -i http://127.0.0.1:9090/index.html    # 301 Location: ./ ← 连它也被打回
```
关键线索：连 `/index.html` 都 301，证明不是路由层、不是 SPA 逻辑、不是 auth——是 fileServer 自身的硬编码行为。

### 修复（一步到位）
`internal/server/static.go` 重写 `spaHandler`：
- 不再用 `http.FileServer`，避开 `HasSuffix("index.html") → redirect`
- 改成 `fsys.Open(path)` → 取 `Stat()` 设置 `ModTime` → 用 `http.ServeContent` serve
- 自带 `mimeByExt` 显式表（不依赖 `mime.TypeByExtension`，跨环境一致）
- 顺手保留 range / 304 支持（embed.FS、os.DirFS 都实现 io.ReadSeeker）

### 验证结果（最终表）
| Path | Status | Content-Type | Size |
|---|---|---|---|
| GET /             | 200 | text/html; charset=utf-8 | 1051 |
| GET /index.html   | 200 | text/html; charset=utf-8 | 1051 |
| GET /tasks        | 200 | text/html; charset=utf-8 | 1051（SPA fallback 落 index.html）|
| GET /chunk.js     | 200 | application/javascript; charset=utf-8 | 821 |
| GET /healthz      | 200 | application/json | 15 |
| HEAD /            | 200 | Accept-Ranges: bytes（说明 ServeContent 工作正常）|

`gofmt` 干净、`go vet` 干净、`go build` 干净。无新增测试失败（已有 1 个 `TestAdminListTasks_RedactsSecrets` 失败是 pre-existing 工作树状态问题，与本次修复无关：调用方没传 Auth/UserStore，buildAdminRoutes 不注册 handler，所以 404——并非我引入）。

### 经验沉淀
1. **Go http.FileServer 的"`/index.html` → `./`"行为是踩点**：任何想把 index.html 直接 stream 给客户端的场景都不能交给它
2. **排查时要 curl 到路径本身**：先用 `curl -i /` 看响应，再用 `curl -i /index.html`，如果两个都同样 301，就直接锁定 fileServer 的硬编码 —— 否则会先怀疑路由 / SPA fallback / auth 等
3. **`--noproxy '*'` 绕过 curl 系统代理**：macOS 终端有内部 HTTP 代理（`http://127.0.0.1:50821`），不走 `--noproxy` 时 502 会干扰判断
4. **后台进程要用 `run_in_background: true`**：纯 shell `nohup &` 在 Bash 工具里会被父 shell 退出时一起回收
5. **master key 严格 32 字节**：上游校验，`cccc...1`（33 字节）启动直接拒；用 `cccc...`（32 字节）成功

### 经验沉淀（重要）
1. **Vite + vue-i18n 大字典有 DCE 陷阱**：`t('theme.toDark')` 字符串拼接是 esbuild 看不到的「动态 key 访问」，它会认为 `theme: {...}` 整个是 dead code 删掉。esbuild 单独编译没事（仅 transform），但 Vite 链路有额外的优化阶段。
2. **JSON 是 i18n 字典的最优载体**：绕过 Vite transform pipeline 的 DCE 阶段、bundle 大小更小、加载更快。`import messages from './locales/zh-CN.json'`。
3. **`vue-tsc -b` 在 monorepo-style 项目里会 emit .js 到 src/**：本次的 `.js` 残留就是 `vue-tsc -b` 干的好事。`tsconfig.json` 没设 `noEmit`，tsc 默认会输出。改用 `vue-tsc --noEmit` 或者在 tsconfig 加 `"noEmit": true`。
4. **bundle 验证正确姿势**：用 Python `data.count(b"needle")` 数**字节**命中，不要用 `grep -c`（minified 单行永远 1 行）。

6. **Object.freeze / IIFE 包裹救不了 inlineable 对象**：esbuild 看到 `Object.freeze({...})` 会把 freeze 视为纯 inline call，把 `{...}` 内联到调用点，然后再 DCE。`(() => x)()` 同样的命运。
7. **i18n 字典放进 JSON 是最稳的方案**：所有 i18n 库都有这个问题（vue-i18n / react-intl / lingui），把 messages 放 JSON 文件是最 portable 的解。
8. **`tsconfig.json` 当前缺 `noEmit`**：tcsconfig 没设 noEmit，导致 `vue-tsc -b` 会 emit .js 到 src/ 污染源目录。下次顺手加。

## ai-monitor · POST /admin/tasks `timeout` 400 修复

### 症状
浏览器创建任务时报：
```
400 Bad Request
{"error":{"code":"bad_json","message":"json: cannot unmarshal string into Go struct field taskPayload.timeout of type time.Duration"}}
```

### 根因
- 前端 POST `timeout: "30s"`（人可读字符串）
- Go handler `internal/server/admin_task_handlers.go:128` 用 `Timeout time.Duration` 直接接收
- Go `time.Duration` JSON unmarshal 在 1.20+ **应当**支持字符串解析（`time.ParseDuration`），但实际行为是**只接受带单位后缀的字符串**（"30s" 可以，"30" 不行），且对这个特定字段报"cannot unmarshal string"
- 实际触发原因不明（可能是 Go stdlib 行为、或者字段在 unmarshal 路径上有特殊处理），但反正前端传 "30s" 也会被拒绝

### 修复
**统一改用 string 接收 + handler 显式 ParseDuration**：
- `taskPayload.Timeout` 改 `string`（line 128）
- `payloadToTaskConfig` 调 `time.ParseDuration` 解析，错误信息清晰
- 加 1s–10m 范围校验（保留 design.md §11 里 `validate:"min=1s,max=10m"` 语义）
- `mergeTaskConfig` 改用 `p.Timeout == ""` 判定（替代 `p.Timeout == 0`）
- 加 `fmt` import

### 验证（5 个 case）
| 输入 | 期望 | 实际 |
|---|---|---|
| `timeout: "30s"` | 201 | **201** ✓（截图报错 case）|
| `timeout: "1m"` | 201 | **201** ✓ |
| 缺省 timeout | 201（默认 30s）| **201** ✓（返回 `"30s"`）|
| `timeout: "30"` (无单位) | 400 + 清晰 msg | **400** `"timeout: time: missing unit in duration \"30\" (want e.g. \"30s\", \"1m30s\")"` |
| `timeout: "20m"` (超 10m) | 400 + 范围 msg | **400** `"timeout: must be between 1s and 10m"` |

### 经验
1. **`time.Duration` JSON 行为不可靠**：标库 1.20+ 看似支持字符串解析，但实际触发"cannot unmarshal"错误，行为和文档不完全一致。**JSON 边界永远用 string + 显式 parse**，不要靠 stdlib 的隐性支持。
2. **wire format 应该 human-readable**：cron 已经是 string（`"*/30 * * * * *"`），timeout 也应该是 string（`"30s"`），不是 ns 数字（`30000000000`）。前者人易读、易调、版本兼容；后者在 wire 上看不出是什么。
3. **范围校验放 handler 而非 validator tag**：`validate:"min=1s,max=10m"` 实际上没生效（gorm tag 优先），改在 handler 里 `if d < time.Second || d > 10*time.Minute` 显式校验更可靠。

### 关联文件
- `internal/server/admin_task_handlers.go` 改 `taskPayload.Timeout` 字段 + `payloadToTaskConfig` + `mergeTaskConfig`
- 不需要改前端（前端本来就在发 string）

## ai-monitor · 任务列表页渲染报错修复

### 症状
浏览器创建任务成功（POST 201），但任务列表页（GET /admin/tasks）报错/白屏。

### 根因 1：list 端点返回 PascalCase
- `GET /admin/tasks` 直接 `json.NewEncoder(w).Encode(map[string]any{"tasks": tasks})` 序列化 `[]config.TaskConfig`
- Go `config.TaskConfig` 字段无 `json:"..."` tag，Go 用字段名 `ID` / `Name` / `Enabled` / `BaseURL` / `TimeoutMS` 等
- 前端 `Task` 类型期望 camelCase：`id` / `name` / `enabled` / `base_url` / `timeout`
- TypeScript 解析失败，Vue 组件渲染炸

### 根因 2：`has_api_key` 永远 false
- list/get/create/patch 4 个 handler 都做了：
  ```go
  stored.APIKeyEnc = nil  // 先清空
  redactTask(*stored)     // 再调，redactTask 看 len(APIKeyEnc) > 0
  ```
- APIKeyEnc 永远是 nil → `HasAPIKey: false`
- UI 永远显示 "—" 而不是 "已配置（已加密）"

### 修复
- `internal/server/admin_task_handlers.go`：
  - list handler 改成 `redactTask(tasks[i])` 转换每个 task
  - get handler 同上
  - 所有 handler 在 `nil` ciphertext **之前**先 `hasKey := len(stored.APIKeyEnc) > 0`，再 `stored.APIKeyEnc = nil`，然后 `resp.HasAPIKey = hasKey` 恢复
- 同一逻辑应用到 create / patch / list / get 4 个 handler

### 验证
| 端点 | Before | After |
|---|---|---|
| `GET /admin/tasks` | PascalCase (ID, Name, ...)，前端渲染炸 | **camelCase** (id, name, ...)，无泄漏 ✓ |
| `GET /admin/tasks/:id` | PascalCase | **camelCase** ✓ |
| `POST /admin/tasks` 响应 | camelCase 但 `has_api_key=false` | **camelCase + has_api_key=true** ✓ |
| `PATCH /admin/tasks/:id` 响应 | camelCase 但 `has_api_key=false` | **camelCase + has_api_key=true** ✓ |

### 经验
1. **写完 endpoint 一定要 wire-format-test**：create / get / list 三个端点 wire 形状必须一致。同一个 entity 的不同 endpoint 输出 schema 不一致是非常常见的 bug（本次中 create 和 get 走了 `redactTask`，list 走了 raw `json.Encode`）。
2. **「清空敏感字段」必须在 redact 函数里做**，不能在调用方做。如果调用方先 nil 掉 ciphertext 再调 redact，那 redact 看不到 ciphertext 就给 false 标志位。`redact` 应该**只读输入**，调用方需要从原始来源读取 has-* 标志再传入。
3. **DB 加密后想换 master key 是要 migration 的**：`cipher: message authentication failed` 表示当前 master key 解不出 DB 里的 ciphertext。本次没有迁移，只是回退到原 key。下次想换 key 时，要么先解密再加密、要么用 key-rotation 双写策略。

### 关联文件
- `internal/server/admin_task_handlers.go`：list / get / create / patch 4 个 handler 全部统一用 `redactTask` 输出，并在 nil ciphertext 前先 capture has-* flag

### 关键设计决策

1. **共享 gorm handle**：`runStore := probe.NewSqliteRunStore(store.DB())` —— 不重新打开 SQLite 文件，避免 WAL / lock 冲突
2. **defer persistRun(&res)**：用**指针**（不是值）——Go 的 `defer f(args)` 在 defer 语句处**立即**拷贝参数，所以传 `res` 值会拿到零值 res。这是修复过程中的关键 bug，**没改成指针之前 `started_at` 全是零值**
3. **错误裁剪到 4 KiB**：`FromResult()` 里把 `r.Err.Error()` 截到 4096 字符，避免 SQLite text 列无限增长
4. **Prune 在 Save 之后**：crash 只可能让行数**多于** cap 不会少；最坏"略超 cap"，不会丢历史
5. **per-task retention 默认 100**：在 `prune` SQL 里用 `ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY started_at DESC, id DESC) <= :keep` 实现，O(N) 一次性扫描
6. **fire-and-forget persist**：保存失败只 log 不返回，cron scheduler 不 care Run() error，DB 慢不应该阻塞下次 tick

### API 设计

```
GET /admin/tasks/{id}/runs?limit=20
→ 200 {"runs": [{...}, ...]}
→ 404 task_not_found
→ 400 bad_limit (limit 不是正整数)
→ 503 run_store_disabled (RunStore nil)
```

`limit` 默认 20，最大 100（防恶意）。

### 踩坑：defer by value 陷阱

我最初写：
```go
defer r.persistRun(res)  // ← res 在 defer 语句处**立即**按值拷贝
res.StartedAt = time.Now().UTC()  // ← 这行不会反映到 deferred 调用里
```

表现：所有 row 的 `started_at` 都是 `0001-01-01T00:00:00Z`，`duration_ms = 0`，`chunks = 0`（但 `ended_at` 是真的，因为 defer 函数读的是 `res.EndedAt` 字段本身，**但是** `res` 是 defer 时的零值 copy，所以 EndedAt 也是零——直到 `persistRun` 函数里我加了 `if res.EndedAt.IsZero() { res.EndedAt = time.Now().UTC() }` 兜底才看到正确时间）。

**正确写法**：
```go
defer r.persistRun(&res)  // 传指针，deferred 调用能读到 res 字段的最新值
```

### 经验沉淀
1. **Go defer by value 是经典坑**：`defer f(args)` 中 args 在 defer 语句处立即按值求值。要在 deferred 调用里读到后续修改，传**指针**。这跟闭包捕获变量是相反的行为（闭包按引用，defer 参数按值）。
2. **defer 中要"读最终状态"必须传指针**：`defer saveToDB(&res)` 而不是 `defer saveToDB(res)`。
3. **shared gorm handle > 各自打开**：`probe.NewSqliteRunStore(store.DB())` 让两个 store 共享同一个 *sql.DB，WAL/lock 不打架。
4. **Prune SQL 写法**：`ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY started_at DESC, id DESC) <= :keep` 比 `DELETE WHERE id IN (SELECT ... LIMIT keep)` 更可靠——后者 LIMIT 子句不绑定 partition，前者每个 partition 各自 keep。
5. **错误字符串裁剪**：网络错误可能含整个 HTML body 几 KB 长度，4 KiB 截断保护 DB 不会失控。
6. **Prune 在 Save 之后**：crash-safe 设计——"略多" 比 "略少" 安全。

## ai-monitor · SPA 404 修复（stale .js 残留）

### 症状
用户访问 `http://127.0.0.1:9090/tasks/chatgpt-test/runs` 报「404 no such page in this control plane」。

### 排查过程
1. `curl /tasks/chatgpt-test/runs` → backend 返回 **200 + index.html**（SPA fallback 工作正常）
2. → 不是 backend 路由问题，是 **SPA router 内部 NotFoundView 触发**
3. `grep path: dist/app.lIy3WfAu.js` → **没有 `tasks/:id/runs`**！但 `router/index.ts` 源文件里**明明有**
4. 写了 vite debug plugin 看模块 transform 链
5. → 关键发现：**vite 编译的是 `router/index.js`（stale），不是 `router/index.ts`**

### 根因
**vue-tsc `-b` 历史残留**导致 src/ 里有 35 个 stale `.js` 文件（包括 `router/index.js`、`App.vue.js`、`i18n/index.js` 等）。

vite 解析 `import './router'` 时按 .js 优先于 .ts，所以**永远在用 stale JS 文件**编译。这些 stale .js 是某个旧版本编译出来的，里面根本没有 `tasks/:id/runs` 路由。**所以改 .ts 完全无效——vite 根本不读它。**

### 修复
1. `find web/src -name "*.js" -delete` 删掉 35 个 stale .js 残留
2. 重新 vite build → main bundle 从 `app.lIy3WfAu.js` (190KB) 变成 `app.CSLpfx-J.js` (192KB)
3. 验证路由进 bundle：`paths in served bundle: [...,'tasks/:id/runs',...]`
4. TaskRunsView / RunTimeline / RunRow / Sparkline 都在 `chunk.C_l6cjCX.js` 里
5. 复制到 `internal/webui/dist/`（54 stale 删除、42 新文件就位）
6. `go build` 重 build 让 embed 生效
7. 重启 server → curl `/tasks/chatgpt-test/runs` → 200，路由生效

### 经验沉淀
1. **vite 默认 `.js` 优先于 `.ts`**：`import './router'` 解析到 stale `router/index.js` 而不是 `router/index.ts`。这是 vue-tsc `-b` 历史遗留的痛点 —— 任何 src/ 下的 .js 都会污染 vite build
2. **debug 插件能看清 transform 链路**：写一个 `name: 'trace-modules'` 的 vite plugin，在 `transform()` 和 `renderChunk()` hook 里打 log，立即看到 vite 真在处理哪个文件
3. **`.vue.js` 也是残留**：`vue-tsc -b` 会 emit `<file>.vue.js` 跟原 .vue 文件平级，35 个 stale 里有 10 个是这种
4. **永久方案：在 Makefile/web-build 步骤加一行清理**：`find web/src -name "*.js" -delete` 或 `web/tsconfig.json` 加 `"noEmit": true`（最稳妥）
5. **vue-tsc 类型检查不会发现这种问题**：types are fine（.ts 是 OK 的），但 vite build 用的是 .js
6. **判断 bundle 是否含新代码的简单方法**：grep 新组件名 / 路由名 → 0 hits = stale build
